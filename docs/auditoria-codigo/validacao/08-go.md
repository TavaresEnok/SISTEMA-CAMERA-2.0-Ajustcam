# Validação do worker Go

## Toolchain exigido

`services/camera-worker-go/go.mod` declara:

```text
module drac-vms/camera-worker
go 1.22
```

O Dockerfile de build também usa `golang:1.22-alpine`. O ambiente desta
auditoria não possui `go` no `PATH`; `go version` retornou `command not found`.
Nenhuma ferramenta foi instalada e nenhuma versão diferente foi usada.

## Comandos recomendados

Executar em ambiente descartável/CI com Go 1.22 compatível, a partir de
`services/camera-worker-go`:

```bash
go test ./...
go test -race ./...
go vet ./...
```

Os comandos não foram executados aqui. Não há arquivos `*_test.go`; portanto,
mesmo com toolchain, `go test` hoje validaria essencialmente compilação. O CI
versionado também não possui job Go.

## Validação estática vinculada ao DRAC-AUD-020

- `camera-worker` é opt-in pelo profile Compose `legacy-worker`.
- O healthcheck consulta `http://127.0.0.1:8000/health`.
- Nenhum arquivo Go cria listener HTTP; o healthcheck falha sempre quando o
  profile é habilitado.
- `fetchCameras` usa `http.Client{}` sem timeout.
- `reportStatus` e `registerRecording` têm timeout de 5 s e 10 s,
  respectivamente, mostrando que a ausência em `fetchCameras` não é uma
  limitação da linguagem.
- O loop principal cria `go processCamera` para cada câmera a cada minuto sem
  controlar se a chamada anterior terminou.
- a gravação usa `exec.Command("ffmpeg", ...)`, sem `CommandContext`,
  tratamento de SIGTERM ou cancelamento; um FFmpeg preso mantém a goroutine.
- `checkCameraRTSP` é melhor protegido: usa `CommandContext` com dez segundos.
- o README ainda chama o worker de placeholder, enquanto Compose e código
  implementam um caminho legado funcional e opt-in.

Severidade revisada: MÉDIA. Confiança revisada: CONFIRMADO. Decisão:
**DEPENDE DE CONFIGURAÇÃO**, porque o runtime padrão não habilita o profile;
quando habilitado, o healthcheck incompatível é confirmado por análise.

## Testes a criar

1. HTTP blackhole: `fetchCameras` precisa terminar no prazo definido.
2. Health/readiness: o endpoint deve refletir Redis, API e capacidade do loop.
3. SIGTERM com FFmpeg sintético preso: processo deve cancelar e sair no grace
   period do container.
4. Repetição de `processCamera`: no máximo uma goroutine por câmera.
5. Corrida: `go test -race ./...` sobre start/stop/reload simultâneos.
6. Registro após timeout e arquivo parcial: definir retry/idempotência.

## Decisão necessária

Escolher explicitamente entre:

- descontinuar e remover o profile legado; ou
- declarar suporte, portar cancelamento/health/testes e alinhar o pipeline de
  gravação com o caminho canônico da API.

Manter um runtime opt-in sem health válido e sem teste Go não é uma terceira
opção segura.
